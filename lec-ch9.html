进阶技巧 —— 从新手到高手

第十篇 · 进阶篇

9.1 进阶之路：从"能用"到"好用"

学完前面的章节，你已经能独立做出个人主页和待办清单并部署上线了。但 Vibe Coding 的世界远不止于此。这一章介绍一些进阶技巧，帮你从"能做出东西"提升到"高效、高质量地做出东西"。

这些技巧不需要一次全部掌握，挑你觉得有用的先试，用熟了再学下一个。

9.2 项目规则文件：让 AI 全程遵守你的规范

在第3章我们提到过项目规则文件。这里详细介绍怎么用。

在项目根目录创建一个规则文件（Trae 用 .trae/rules，Cursor 用.cursorrules），AI 工具会自动读取，在整个项目中遵守你的规则。

9.2.1 规则文件示例

# 项目规则

## 技术栈
- 纯 HTML/CSS/JavaScript，不使用任何框架和库
- CSS 使用 Flexbox 布局，不使用 Grid
- JavaScript 使用 ES6+ 语法，优先使用箭头函数和 const/let

## 编码规范
- 变量和函数使用 camelCase 命名
- 代码中必须加中文注释
- 缩进使用 2 个空格
- 字符串使用单引号
- 函数长度不超过 50 行，超过则拆分

## 设计规范
- 主色调：#3b82f6（蓝色）
- 圆角：8px
- 字体：系统默认无衬线字体栈
- 设计风格：简洁现代，不要花哨动画
- 所有可点击元素加 hover 效果和 transition 过渡

## 安全要求
- 用户输入必须经过转义后再插入 DOM，防止 XSS
- 不使用 eval()
- 不使用 innerHTML 插入用户输入内容，用 textContent
- localStorage 不存储敏感信息

## 性能要求
- 动画使用 transform 和 opacity，不使用 width/height/top/left
- 图片加 loading="lazy" 懒加载
- 减少不必要的 DOM 操作

## 其他
- 兼容 Chrome 和 Edge 浏览器
- 响应式设计，375px 宽度以上正常显示
- 所有功能必须有对应的中文注释说明

9.2.2 使用技巧

  • 项目开始时创建：第一轮对话前就创建好规则文件，AI 从一开始就遵守
  • 逐步完善：不需要一次写全，做项目过程中发现 AI 总犯某个错，就加到规则文件里
  • 不同项目不同规则：每个项目可以有自己的规则文件，技术栈、设计风格不同就写不同的规则
  • 配合提示词使用：规则文件管"全局规范"，具体提示词管"当前任务"，两者配合效果最好

9.3 多模型组合策略：不同任务用不同 AI

没有一个 AI 是万能的，不同模型有不同的擅长领域。学会组合使用，效率翻倍。

9.3.1 各模型特点对比

模型擅长不擅长推荐场景
豆包中文理解、文案创作、需求梳理、简单代码复杂算法、大项目架构日常对话、写文案、梳理需求、简单代码生成
DeepSeek V3代码生成、代码审查、技术问题解答创意写作、设计审美写代码、找 bug、代码审查、技术问答
DeepSeek R1复杂推理、算法、逻辑问题速度慢、简单任务大材小用复杂算法、疑难 bug、架构设计
GPT-4o多模态（看图写代码）、综合能力强、英文资料国内访问不便、收费根据设计图写页面、复杂项目、英文技术问题
Trae（内置模型）项目级开发、文件操作、上下文完整脱离项目的独立问答在 IDE 中做完整项目、多文件开发
Grok实时信息、另类思路代码质量不稳定查最新技术动态、换个思路解决问题

9.3.2 组合使用实战

  • A 生成 + B 审查：用 Trae/豆包生成代码，然后把代码贴给 DeepSeek 让它审查找 bug。不同模型的盲点不同，交叉审查能发现更多问题。
  • 对话工具梳理 + IDE 实现：先在豆包里把需求聊清楚、梳理成结构化的需求文档，再拿到 Trae 里实现。避免在 IDE 里边想边做导致反复修改。
  • 卡壳换模型：一个模型连续 2-3 次给不出满意结果，换另一个模型试试。有时候换个模型问题就迎刃而解。
  • 复杂问题用 R1：遇到疑难 bug、复杂算法，用 DeepSeek R1 推理模型，它会一步步思考，解决率更高。
  • 设计图转代码用 GPT-4o：有 UI 设计稿想转成代码，用支持多模态的 GPT-4o，看图写代码更准。

9.4 上下文管理：让 AI 始终"记得"你的项目

AI 的上下文窗口是有限的，对话太长就会"忘记"之前的内容。学会管理上下文，能让 AI 始终保持对项目的准确理解。

9.4.1 什么时候需要清理上下文

  • 对话超过 15-20 轮
  • AI 开始忘记之前的决定（比如你说过用蓝色，它又改成红色）
  • AI 给出矛盾的建议
  • AI 引用不存在的代码或文件
  • AI 回复变慢或质量明显下降

9.4.2 上下文管理技巧

  1. 定期总结：对话进行到 10 轮左右，让 AI 总结当前项目状态："请总结当前项目的已实现功能、文件结构、技术栈、待办事项。"
  2. 新建对话：把总结复制下来，新建一个对话，把总结作为第一条消息粘贴进去，然后继续开发。AI 带着完整的项目记忆开始新对话。
  3. 项目规则文件：如 9.2 所述，把不变的规范写进规则文件，不需要每次在对话中重复。
  4. 分模块对话：大项目分成多个模块，每个模块单独开对话。比如"样式优化"一个对话，"功能开发"另一个对话。
  5. 关键信息置顶：在对话开头或规则文件中写明关键约束（技术栈、设计风格、文件结构），AI 不容易忘。
  6. 及时纠正：发现 AI 记错了，立刻纠正："不对，之前决定的是用蓝色 #3b82f6，不是红色。请记住。"

9.5 Git 版本控制入门：给你的项目上"保险"

做项目过程中，你是不是遇到过：改着改着改坏了，想回到之前的版本但回不去了？Git 就是解决这个问题的——它能记录你的每一次修改，随时可以回退到任何历史版本。

9.5.1 为什么 Vibe Coding 更需要 Git

  • AI 改代码可能改坏，有 Git 就能一键回退
  • 每完成一个功能就提交一次，形成清晰的版本历史
  • 可以创建分支尝试新功能，失败了就删掉分支，不影响主版本
  • 和 GitHub Pages 部署结合，push 即部署
  • 以后找工作，GitHub 上的提交记录就是你的作品集

9.5.2 Git 基础命令

# 初始化仓库（项目文件夹里执行一次）
git init

# 查看当前状态（哪些文件改了）
git status

# 添加所有修改到暂存区
git add .

# 提交（写一句说明，比如"完成添加任务功能"）
git commit -m "完成添加任务功能"

# 查看提交历史
git log

# 回退到上一个版本（改坏了用这个）
git reset --hard HEAD~1

# 查看某版本和当前版本的区别
git diff HEAD~1

# 关联远程仓库（GitHub）
git remote add origin https://github.com/用户名/仓库名.git

# 推送到 GitHub
git push -u origin main

# 以后推送
git push

9.5.3 Vibe Coding 中的 Git 工作流

  1. 项目开始：git init，提交初始版本
  2. 每完成一个功能：git add . → git commit -m "完成XX功能"
  3. AI 改坏了：git reset --hard HEAD~1 回退到上一个正常版本
  4. 想尝试新功能：git branch 新功能名 → git checkout 新功能名，在分支上做，成功了合并回主分支，失败了删掉分支
  5. 部署：git push 到 GitHub，GitHub Pages 自动部署

新手建议：先学会 git add、git commit、git status、git reset 这四个命令，足够你做版本回退了。分支、合并等高级功能等你熟练了再学。Trae 里也有图形化的 Git 界面，不用记命令也能操作。

9.6 代码审查方法：让 AI 的代码更可靠

AI 生成的代码不是完美的，学会审查能帮你发现隐藏的 bug 和安全问题。

9.6.1 审查清单

审查维度检查什么
功能正确性所有需求都实现了吗？边界情况处理了吗？（空输入、超长文本、特殊字符、快速连续点击）
安全性用户输入直接插入 DOM 了吗？（XSS 风险）有 eval() 吗？有硬编码的密钥吗？
性能有不必要的循环吗？频繁操作 DOM 吗？动画用了 width/height 吗？图片没懒加载吗？
代码质量变量名有意义吗？有重复代码吗？函数太长了吗？有注释吗？
可维护性结构清晰吗？模块化了吗？以后好改吗？
兼容性用了过时的 API 吗？浏览器兼容性如何？

9.6.2 让 AI 自我审查

你不需要自己逐行审查，让 AI 来做：

请以资深前端工程师的视角，严格审查下面的代码。

审查维度：
1. 功能正确性：有没有逻辑错误？边界情况处理了吗？
2. 安全性：有没有 XSS 风险？有没有 eval()？
3. 性能：有没有性能问题？
4. 代码质量：命名、重复代码、注释
5. 可维护性：结构是否清晰

对每个问题，按以下格式输出：
【问题等级：🔴严重 / 🟡中等 / 🟢轻微】
- 问题描述：
- 位置：
- 修复建议：
- 修复后代码：

最后给出总体评价和最重要的 3 个改进建议。

代码如下：
【粘贴代码】

9.6.3 交叉审查

用 A 模型生成的代码，让 B 模型审查。比如 Trae 生成的代码，贴给 DeepSeek 审查。不同模型的关注点不同，交叉审查能发现更多问题。

9.7 安全注意事项

Vibe Coding 做项目时，有几个安全问题需要注意：

⚠️ 安全注意事项
  1. 不要把 API Key 写在前端代码里：前端代码任何人都能看到（F12 查看源代码）。如果需要调用 AI API，密钥应该放在后端。本课程项目不需要调用 API，用工具的对话功能就行。
  2. 防止 XSS：用户输入的内容不要直接用 innerHTML 插入页面，用 textContent，或者先转义。待办清单中用户输入的任务文字，如果用 innerHTML 插入，用户输入<script>恶意代码</script> 就会被执行。
  3. localStorage 不存敏感信息：localStorage 里的数据用户可以在开发者工具中看到和修改。不要存密码、身份证号、银行卡号等敏感信息。
  4. 部署的公开项目不要含敏感信息：GitHub 公开仓库任何人都能看。代码里不要写你的手机号、住址、密码等。提交前检查一下。
  5. AI 生成的第三方库要核实：如果 AI 建议引入某个库，先确认这个库是真实存在的、安全的。AI 可能"幻觉"出不存在的库。
  6. 不要运行看不懂的命令：AI 让你在终端运行命令时，如果看不懂，先问清楚这个命令是干什么的。特别是包含 rm、sudo、curl | bash 等的命令。

9.8 持续学习路径

学完本课程后，如果你想继续深入，可以按以下路径学习：

9.8.1 巩固 Vibe Coding 能力

  • 多做项目：个人博客、计算器、天气应用、记事本、番茄钟、小游戏等
  • 建立自己的提示词库和代码片段库
  • 尝试更复杂的项目：多页面网站、带后端的应用

9.8.2 学习前端基础知识

  • 系统学习 HTML/CSS/JS（MDN 文档、freeCodeCamp、菜鸟教程）
  • 学习一个前端框架（Vue 或 React），AI 时代了解框架概念即可
  • 学习浏览器原理、网络基础（HTTP、HTTPS）

9.8.3 学习工程化能力

  • Git 进阶：分支、合并、冲突解决、GitHub 协作
  • 构建工具：Vite、Webpack（了解概念）
  • 代码规范：ESLint、Prettier
  • 测试：单元测试、E2E 测试（了解概念）

9.8.4 拓展 AI 能力

  • 学习 AI Agent 的使用（Trae SOLO 模式、Cursor、Devin 等）
  • 学习 MCP（Model Context Protocol），给 AI 接更多工具
  • 学习提示词工程进阶：Chain of Thought、Few-shot、ReAct 等
  • 尝试用 AI 做全栈应用（前端 + 后端 + 数据库）

最重要的学习方法：做项目。不要陷入"学完所有知识再做项目"的陷阱。边做边学，遇到问题再查，是最高效的学习方式。Vibe Coding 让你能快速做出东西，从做东西中获得成就感和反馈，驱动你持续学习。

✅ 本章小结

本章关键点：

  1. 项目规则文件：在项目根目录创建规则文件，定义技术栈、编码规范、设计规范、安全要求，AI 全程遵守。
  2. 多模型组合：不同模型擅长不同领域。A生成+B审查、对话工具梳理+IDE实现、卡壳换模型、复杂问题用R1、设计图转代码用GPT-4o。
  3. 上下文管理：对话15-20轮后让AI总结，新建对话粘贴总结继续。用规则文件减少重复信息。分模块开对话。
  4. Git 版本控制：git init/add/commit/status/reset 五个命令入门。每完成一个功能提交一次，改坏了一键回退。和 GitHub Pages 结合，push即部署。
  5. 代码审查：用审查清单（功能/安全/性能/质量/可维护性/兼容性）检查。让AI自我审查，或交叉审查（A生成B审查）。
  6. 安全注意：API Key 不写前端、防XSS、localStorage不存敏感信息、公开仓库不含隐私、不运行看不懂的命令。
  7. 持续学习：多做项目、学前端基础、学工程化、拓展AI能力。最重要的是边做边学，不要等"学完再做"。
